# Q26 報告：突破後の「出し手のパスと受け手の動きが合わない」の独立検証

この報告は原因の切り分けと、次に行う最小の検証案までです。
- AI本体の変更、90分試合、正式統合はしていません。新しい候補も作っていません。
- 原本 ZIP と過去の各版、受け取った2つの資料は変更していません。展開物は別の場所で読み取り専用として使いました。
- 未来の情報を選手に与える提案はしていません。受け手自身の計画や真の位置は、監査用のラベルとしてだけ使っています（§9）。

## 0. 要点

1. **受け取った資料は正しく再現できました。**
   - 7場面セットは、Node 22 で同梱の検証器を走らせて7件すべて PASS です。I17 の原本の標準エンジンに差し替えても7件すべて PASS でした。
   - 同梱の研究枝（base_off）は、import の書き方を除いて I17 標準とコードが同一です。依存ファイル1,059件も I17 原本と同一でした。
   - 3版比較の「基準」の記録は、7場面セットの `outlet_unreached` の期待記録と全フレーム・全ログ行で一致しました。
2. **「飛行時間連動候補」は、I17 にすでにある計算と同じものでした。**
   - I17 標準の通常パス・事前予約パスの狙いは、受け手の観測位置に、観測速度の **0.35秒分だけ**を足した点です（`outgoing_candidates_legacy.mjs` 14行目）。球の速さは距離に応じて上がるので、遠いパスほど飛行時間が長くなりますが、先読みは 0.35秒のままです。
   - I17 標準には、飛行時間に合わせた到達点の計算（PAI1、`pass_arrival_aim.mjs`）が**すでに入っています**。ただし使われているのは、球際で球を離す特別な経路（`ball_release.mjs`）だけです。
   - 候補が記録した狙いは、同じ観測に PAI1 をかけた結果と 0.001〜0.058m で一致しました（記録で狙いが変わった4回すべて）。
3. **出し手が知れた情報は正確でした。** 受け手の位置の誤差は 0.2m 以内、速度の誤差は 0.2〜1.6m/s です。出し手の知覚を直す必要は見当たりません。
4. **受け手は、パスの予定を知らずに自分の計画で動いています。**
   - キック時の受け手は、多くが自分の support の目標へ向かっていました。その目標までは 3.4〜12.6m で、速い受け手は 0.5〜0.7 秒でそこに着く距離です。
   - 受け手が動く球を見て受球の判断に切り替えるのは、キックから 0.25〜0.45 秒後です（1件だけ 0.8 秒）。これは成功例と失敗例で同じでした。
5. **成否を分けたのは「受け手の最初の受球目標が、自分の進む向きの前か後ろか」でした。** 走っている受け手（キック時 4.5m/s 以上）で比べています。
   - **失敗3件**（12171、42190 の基準、受球V2 の 42170）：球が受け手の背後を横切り、最初の受球目標が 1.5〜3.6m 後ろになりました。受け手は 0.4〜1.6m/s まで減速し、球に届かず（最接近 1.5〜3.4m）、こぼれ球を相手が拾いました。
   - **成功2件**（12367、42190 の候補）：最初の受球目標が 1.9〜5.5m 前でした。受け手は走り続け、0.7m 以内で受けました。
   - 42190 の基準では、球が受け手の走る向きに約49°で飛び、受け手の約3m前を横切ってそのまま 9m/s 超で転がりました。受け手は 6.8m/s から 0.6m/s まで 1.3 秒かけて止まり、届きませんでした。
6. **失敗をすべて欠陥とはしていません。** 次の3つは、先読みとは別の理由です。
   - **自然なミス（受球の実行）**：6073 は受け手が届いたものの、正面から全速で向かったため相対速度 14.4m/s で `miscontrol` になりました。これはちゃつぴの受球の範囲です。
   - **相手の良い対応**：42258 は相手 A09 のほうが近く、先に触りました。
   - **正常な連係**：12264（静止した受け手）、12367、78414（長いパスで、止まって戻る時間があった）、12242（すぐ別の味方が触った）は守るべき対照です。
7. **候補で「正常な連係が途切れた反例」は、受け取った資料の中には実データがありません。**
   - 3版比較の記録で候補のパスは1本だけで、それはつながった例です。報告に名前の出ている反例（27182、2162、771 の 1002、受球V2 の 87312949）は、データが同梱されていないため確認できませんでした。
   - かわりに、同じ観測に PAI1 をかけた場合の狙いを幾何で調べました。正常に受けた 12367 と 78414 では、狙いが受け手自身の support の目標より 7.4〜9.6m 先になります。これが「途切れる」おそれのある反例の候補です（§5。シミュレーションではありません）。
8. **次に検証すべき変更を一つに絞りました。** 通常パスと事前予約パスの狙いの先読みを、固定 0.35秒から、I17 にすでにある PAI1 の到達時間に置き換えることです（＝既存の候補そのもの）。これを7場面の同じ状態で、事前に決めた判定で確かめます（§6）。
   - 実行には、資料に同梱されていない候補のコード（`pass_prediction/source`）が必要です。

## 6. 次に検証すべき変更（一つ）と最小検証案

### 6.1 変更は一つ
- **内容：** 通常パスと事前予約パスの狙いの先読みを、固定 0.35秒（`outgoing_candidates_legacy.mjs` 14行目）から、I17 にすでにある PAI1 の到達時間（`evaluateArrivalPassCandidate`。`ball_release.mjs` で使用中）に置き換える。
  - これは既存の飛行時間連動候補と同じ計算です（記録上 0.06m 以内で一致）。新しい候補ではなく、既存の候補をそのまま検証します。
  - 係数は足しません。受け手側（受球V2）、受け手の反応の早さ、キックの速さの式は変えません。
- **これを選ぶ理由：**
  1. 出し手の観測は正確なので、知覚の変更は要らない。
  2. 受け手の反応の遅れは成功・失敗で同じで、早めるには受け手にパスの予定（相手の意図）を渡す必要がある。これは未来情報・共有意図にあたるので行わない。
  3. 受け手側の変更（受球V2）は改善せず、出し手の時刻まで変えた（既存の結果）。
  4. 成否を分けた「最初の受球目標が前か後ろか」は、出し手の狙いでほぼ決まる。
- **使う情報：** 出し手本人の観測（受け手の位置と差分速度、球）だけです。受け手の計画や真の位置は使いません。

### 6.2 最小検証案（判定を先に決める）

- **状態：** 7場面の入力保存（I17 標準の保存。I17 原本で直接読める）。3版比較と同じく、同じ内部状態を各版の `fromFixture` に入れます。比べるのは I17 標準と既存の候補の2版だけです。
- **記録：** 最初の判断差 → キック差 → 受け手の最初の受球目標（前／後ろ）→ 最低速度 → 最初の接触（制御の有無）→ 次のプレー → 相手の関与。本報告の `pass_trace.py`、`receiver_reaction.py` をそのまま使えます。
- **事前の判定：**

| 区分 | 場面 | 合格の条件 |
|---|---|---|
| 直るべき失敗 | 12171（recovery_failure） | 受け手の最初の受球目標が前になり、1.1m 以内に届く。届かなければ「先読みでは直らない例」として記録する（12171 は観測速度が加速に遅れていた例） |
| 守る成功 | 12367・12264・12242（breakthrough_outlet）、78414（outlet_to_shot） | 受け手（または元と同じ味方）が制御し、次のプレーへつながる。**一つでも途切れたら反例として残し、不採用のまま** |
| 欠陥と数えない | 6073（contact_failure）、42258、相手のこぼれ球の回収 | 結果が変わっても良し悪しを決めない。miscontrol は受球の担当へ |
| 追加の確認 | 狙いがタッチラインから 5m 以内になる場面（6176 など）、球速の増加 | 球外の増加、到達時の相対速度（受球の限界の目安 10.7m/s）を記録 |
| 未確定 | 窓の中で球が届かない場面 | 窓を延ばして判断するか、未確定のまま |

- **契約：** OFF（I17 標準）の一致、保存・復元、乱数・イベント順は、7場面セットの検証器で基準側を固定済みです。候補側は候補自身の保存で往復を確認します（名札は付け替えない）。
- **必要なもの：** 候補のコード（`pass_prediction/source` と `baseline_source`）。今回の資料には同梱されていないため、こちらでは実行できませんでした。
