## 5. 受け手側の要因：受球の決断が「今の球との距離」で遅れる

- **コード：** `decision.mjs` 60〜62行目。受球（receive／intercept）の点数は、今の球との距離で下がり、自分より球に近い味方が1人いるごとに 0.22 下がります。`cover` の 0.65 を超えるまで受球を選びません。球が自分の方へ来るか（迎え撃つ点や到達時間）は点数に入っていません。
- **実測：** 34本のパスで、受け手の最初の受球判断までの時間を、キック時の球との距離で並べました（`eval/commit_vs_distance.txt`）。

  | キック時の受け手と球の距離 | 最初の受球判断 |
  |---|---|
  | 15m 未満 | 0.05〜0.3秒 |
  | 19〜25m | 0.4〜0.85秒 |
  | 30m 超 | 1.05〜1.3秒 |

- **遠くても成功する例はあります。** 60143（34m、ほぼ静止した受け手）、24405（33m）です。失敗には「速く走る受け手」＋「長い先読み」＋「遅い決断」の3つがそろう必要がありました（60288）。
- **引き渡し（ちゃつぴ・受球）：** 受け手が「自分宛てのパスかもしれない」と知るのは、球との距離が縮んでからです。出し手の宛先は受け手に伝わらないので、伝えるのは共有意図にあたります。
  - 本人の観測（球の向きと速さ）から、迎え撃てる点と時間を受球の決断に使う案は、受け手側の変更なので、こちらでは作りません。
  - 状態：60000 の入力、`rec/60000_flight.json.gz`、`eval/timeline_60288_flight.json`。

## 6. 次に検証すべき変更（一つ、Q26 から更新）と最小検証案

### 6.1 変更は一つ
- **内容：** 既存の飛行時間連動（14行目）に、条件を一つだけ加えます。
  - 出し手が見て、受け手が「今すぐ受球を選べる距離」にいるときだけ、飛行時間の先読みを使います。それ以外は元の 0.35秒です。
  - 「受球を選べる距離」は新しい係数ではなく、既存の受球と cover の点数の式から決まります。press 0.5、球に近い味方0人で約 24.5m、1人で約 19.9m、2人で約 15.3m です。
  - 出し手が使うのは、本人の観測（受け手と球の位置、球に近い味方の数）だけです。
- **選んだ理由：**
  1. 候補の改善例（42190、受け手 11m）と、守られた例（12367 の 7m、6176 の 10m）は、どれも受け手が近く、すぐ決断できた場面だった。
  2. 反例 60288 は、受け手が遠く（30m、近い味方2人）、決断が 1.05秒遅れた場面だった。
  3. 受け手側の決断の遅れそのものはちゃつぴの担当なので、こちらで変えない。
- **根拠が弱いこと：** 反例の実データは1件です。6158（受け手 19m、観測速度より遅く減速していた）は、この条件では防げません（残る反例）。仮説として扱います。
- **組み合わせない：** ちゃつぴが受け手側の決断を変える場合は、この条件と同時に検証しないでください。どちらが効いたか分からなくなります。

- **事前の判定：**
