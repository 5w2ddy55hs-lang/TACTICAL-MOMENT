# Q28 受け手の到達点判断：汎用探索の「2秒末尾点」の独立監査

対象は TACTICAL MOMENT I17 標準（`integration_i8_standard`）です。

- AI・原本・過去の履歴は変更していません。
- 新しい候補、試合の再演、正式採用はしていません。採否の状態は変えていません（K20/L21 保留、M22・P25 不採用のまま）。
- 出し手の飛行時間案は Astra の担当なので、その試験は作っていません。
- 行ったのは2つだけです。
  - 添付パック自身の検査の再実行（コピー上）。
  - 保存済みの本人観測 DTO に、既存の純関数（`choose`、`receptionPlan`、`estimatedArrival` と、比較のために既存の V2 受球・ゾーン守備）を読み取り専用で当てること。

時刻は 20 tick/秒です。フレームの stateTick=T は T を処理する前の状態、イベントの tick=T は T の処理中に起きたものです。

記号は次のとおりです。

| 記号 | 意味 |
|---|---|
| **DP** | 専用の受球計画（`receptionPlan`）を使った |
| **FE** | 汎用探索で距離条件を満たす点があった（数字は満たした時間 t 秒） |
| **EX** | 20点すべて不成立で、末尾点（t≈2.0）が残った |
| **VU** | 球速が不明 |

## 0. 要点

1. **観測は正しい（事実）。**
   - 汎用探索は 0.1〜2.0 秒の20点を順に試します。どれも距離条件を満たさないと、最後に代入した t≈2.0 の点（場内に丸めた点）が目標として残ります。このとき eta は `2.0000000000000004` です。
   - 専用計画があれば、それで上書きされます（`decision.mjs:50-52`）。
   - 添付14窓の receive 判断 3,647件のうち 2,458件（67%）がこの状態でした。
   - 記録された目標は、全3,647件で私の独立再計算と一致しました。

2. **起きる場面の大半は、球がすでに本人の横を過ぎて遠ざかる「追走」です（事実）。**
   - 2,458件中 2,262件は、本人の観測で見ると最接近がすでに過去でした。
   - 2,305件（94%）は、判断が適用される（判断の0.1秒後）前に最接近が来ていました。
   - 追走 1,718件では、2秒点へ向かう方向と、球そのものへ向かう方向の差は中央値 7°でした。20点のどれを選んでも、走る方向はほとんど変わりません。

3. **パスの指定受け手がこの状態になったのは15本です。全15本で、この状態は球が受け手を過ぎた後（または本人の非制御接触の後）に始まりました（事実）。**
   - したがって「受けられなかったこと」をこの処理が引き起こしたとは言えません（推論、根拠は強い）。
   - その後に球を得たのは、味方5・相手8・プレー外1・窓の終了1で、ばらばらでした（事実）。

4. **失敗例 outlet_unreached（A10）では、決め手は2秒点より前の段階です（事実）。**
   - 2秒点の判断は 42216 で、適用は 42218 です。真の最接近は 42219（3.0m）でした。
   - それより前の 42196〜42212 の経過は次のとおりです。
     - 専用計画は最後の判定「0.8m 以内に届く候補なし」で不成立でした。
     - 汎用式は t=0.4〜0.6 の点を「到達可能」と判定しました。
     - A10 は 6.0 → 0.6m/s まで減速しました。
     - 既存の身体予測では、その点に 2.8〜6.4m 届きません。
   - 2秒点は、外した後の追走に使われただけです。
   - 42251 の B07 のキックは、相手の妥当な対応と読みます。

5. **成功例はいずれも、受球まで専用計画が続いていました。2秒点は使われていません（事実）。**
   - 成功例：breakthrough_outlet の A07・A09、outlet_to_shot の A10、far_receiver の B05。
   - far_receiver では、近い味方 B06/B07 が2秒点で追走している間に、奥の B05 が専用計画で制御しました。

6. **既存の別処理は、この状態をほとんど扱っていません。**
   - 専用計画（R07B）も受球 V2（L21、保留中）も、2,458件に対して 0件でした。
   - ゾーン守備には「到達不能のときの外向き cover」があります。作者はコメントで「2秒探索の完了は、可行点がないことを意味しうる」と書いており、この状態を**認識していた**証拠です。ただし次の理由で、この記録には効いていません。
     - ゾーン守備は全記録で無効でした。
     - 発動条件（CB/FB、ハーフラインを越えている、球が前方）に当たる件数は 0件でした。
   - K20/L21/M22 は保持の点数側の変更で、目標点には触れていません。
   - 飛行時間案は出し手側の変更です。`decision.mjs` と `reception.mjs` は I17 と同一でした。

7. **判断**

## 2. コードで確かめた事実

ファイルはいずれも I17 原本の `source/integration_i8_standard/` の下です。

### 2.1 末尾点が残る仕組み

`core/decision.mjs:50-52`

```js
let intercept=bp,eta=2.0;
if(ball.velocityKnown){for(let t=0.1;t<=2.001;t+=0.1){const q={…clamp(bp+v*t*0.82)…};intercept=q;eta=t;if(dist(p,q)<(4+p.abilities.pace*0.04)*t+0.8)break;}}
const reception=!canPlay&&!visibleHolder&&!theirPossession?receptionPlan(o):null;if(reception){intercept=reception.target;eta=reception.eta;}
```

- `intercept` には、条件を満たすかどうかを調べる**前に**、各点が代入されます。
- そのため20点すべてが不成立だと、t≈2.0 の点が残ります。
- 浮動小数の足し算のため、eta は `2.0000000000000004` になります。
- t=2.0 でちょうど成立した場合（今回 30件）も eta は同じ値です。判断の理由文字列も同じなので、**記録だけでは区別できません**。区別するには再計算が要ります。

**点の作り方**
- 観測した球の位置から、球速の 0.82 倍で直線に進めた点です。
- 高さとバウンドは考えません。
- 場外に出る点は、x と y を別々に場内に丸めます。

**到達の判定**
- 判定は「距離 < (4+0.04×pace)×t+0.8」です。
- 本人の今の速度、加速、0.1秒の適用待ちは入っていません。

### 2.2 専用の受球計画

`core/reception.mjs:11-18,38`

計画が null になるのは、次のどれかに当たるときです。

- 球が高い（z≥0.5）、または本人が GK
- 球速が不明
- 観測が古い（0.25秒を超える）
- 球速が 3 m/s 以下
- 本人の観測で最接近がすでに過去（tClosest≤0）、または 1.5秒より先
- 最接近点に最高速でも届かない
- どの候補も 0.8m より外れる

### 2.3 点数は到達できるかどうかを使わない

`core/decision.mjs:60-62`

- receive の点数は、球までの距離・前に出る強さ・観測の古さ・自分より球に近い味方の数で決まります。到達できるかどうかは入りません。
- 末尾点の 2,458件では、2番目の候補はすべて cover（0.65）でした。receive の点数はそれより中央値で 0.51 高く、到達できなくても追走が選ばれます。

### 2.4 時間軸：判断・適用・動き・接触

| 段階 | 時刻 | 内容と根拠 |
|---|---|---|
| 判断 | T | 処理前の状態 T を本人が観測し、`choose` を呼ぶ。記録される判断は、後の合成処理まで済んだもの（`core/engine.mjs:164-205`）。今回の receive 3,647件では、記録の種類と目標が `choose` の結果と全件一致し、合成で目標は変わっていない |
| 適用 | T+2 | 「Boundary B」で `p.action` に入り、同じ tick の移動から使われる（`core/engine.mjs:207-208`） |
| 動き | T+2〜 | `navigationTarget`／`steerAgent`（`core/kinematics.mjs`、`shared/movement.mjs`）が目標へ加速・制動する。**eta は動きに使われない**。末尾点は本人から (4+0.04×pace)×2+0.8 m（この窓で receive を選んだ選手の pace は 62〜74 なので 13.8〜14.7m）以上離れているので、常に全速側になる |
| 次の判断 | T+4〜T+6 | `core/engine.mjs:149` の 4+⌊(100−decision)/35⌋ による。記録では間隔 4 tick が 23,112回、5 tick が 6,888回 |
| 次の適用 | T+6〜T+8 | 末尾点が「残る」のはこの時点まで（0.2〜0.3秒）。毎回、新しい観測から作り直される |
| 接触 | イベント tick | その tick の処理中に起きる |

### 2.5 作者がこの状態を認識していた証拠

`core/zonal_defence.mjs:95-104`

- コメントは次のとおりです。
  > A completed two-second search can mean no feasible sample was found. Only stop an overextended back already beyond halfway. … a failed catch prediction is not permission to pin them near their own goal.
- 処理の内容：eta が 1.99 より大きく、かつ末尾点が到達範囲の外なら、`zonal_unreachable_outward_cover` に置き換えます。
- 対象は、ゾーン守備が有効で、CB/FB がハーフラインを越えていて、球が前方へ向かう場合だけです。
- コメントには「深い守備者は止めない」とあり、扱う範囲を意図して狭くしたと読めます。
- 同じファイルの `recedingRecovery` は逆側の問題（0.1秒先の点で横にブレーキしてしまう）を扱うもので、これもゾーン守備専用です。

### 4.3 断定できるか

- 2秒点が結果を引き起こしたとは**断定できません**。理由は次の5つです。

  2. 追走の大半では、どの点を選んでも走る向きがほぼ変わりません。
  3. 結果がばらばらです（味方5・相手8・その他2）。
  4. 相手の妥当な奪取があります（B07 42251、A09 42299）。
  5. 同じ状態から比べる反実仮想の実行はしていません（今回の指示による）。
