## 3. 監査の定義と読み方の注意

- **球志向判断**：選手の最新判断 kind が press / intercept / receive / save のいずれか。保持者本人と、そのパスの狙われた受け手は除外。これは「判断」であり、実際の距離や接触の数ではありません。
- **文脈**：最後の制御（キック、または control=true の接触）のチームと、球との距離から、own_carry / opp_carry / own_pass_flight / opp_pass_flight / loose に分けました。
- **同一目標**：球志向の味方同士の判断目標点が2m以内。
- **中央空き**：相手保持中で、球が自陣ゴールから40m以内のとき、ゴールから30m以内かつ |y−34|<14 の帯に、球志向でない自チームのフィールド選手が0人。再開後3秒は除外。
- **背後フリー**：相手フィールド選手が自チーム最深のフィールド選手より後方、かつ球より手前にいて、4m以内に自チーム選手がいない状態。再開後3秒と球保持者は除外。オフサイド判定とは別の、監査用の幾何定義です。初版の定義では、CKのキッカーなどを誤検出していたため修正しました。
- **接触の扱い**：イベントの `contact` 行は球と身体の接触のサブステップ記録で、1回のタッチで複数行出ます。本監査では、同じ選手の2tick以内の行を1タッチにまとめています。`body_contact` は選手同士の接触の解決行で、同じペアの3tick以内を1エピソードにまとめています。どちらも衝突回数ではありません（例：771 OFF では球接触行 7,795 に対してタッチ 2,070）。
- **守備失敗と断定しない**：「中央空き」「前進を許した」は幾何上の状態や結果であり、その場面で最善だった行動が何かは判定していません。
- **分岐後の比較**：OFF/ON の比較や枝間比較は、初期状態が同一でも、最初の分岐以降は別の試合です。比較できるのは件数や割合だけで、「同じ機会での成否」ではありません。同じ機会として比べたのは、最初の分岐点だけです（CKは§6）。

## 5. 完成を妨げている課題（重要度順・最大5件）

### 課題1　球への過剰集中と役割重複：共同プレスと群がりを区別する仕組みがない

- **具体例**：C-1（771 OFF、tick 15540–15800）、C-2（771 OFF、57530–57780）、C-3（771 **ON**、7500–7650：5人が5.8秒追走）、C-4（31337 OFF、4250–4370：自陣で4人が5.3秒追走）、D-1 / D-3（中央空き→シュート・得点）。
- **対照**：X-1（2人共同プレスで1.5秒奪取）。
- **確認できた事実**：§4.1、§4.2 のとおり。条件（OFF/ON、kickoff B、未使用seed）をまたいで 49〜58% の範囲で安定しています。ONでも人数は減っていません（52.2% → 53.8%）。ONでは、自チーム保持中に球を追う味方が 15.5% → 11.3% に減っており、効いているのは保持側の局面です。
- **原因仮説**（コード読解。因果は未検証）：`source/integration_i8_standard/core/decision.mjs` の60〜61行目では、球へ向かう候補の点数が `1.65 − 0.048×距離 + 0.35×press − 0.22×min(2, 自分より球に近い味方数)` で、cover / support の0.65と比べられます。味方の数による減点が2人分で頭打ちになるため、自分より近い味方が何人いても、球から約15m以内の全員が球へ向かう計算になります。目標点は全員が同じ予測接触点（intercept / receive）を使うので、目標がそのまま重なります。zonal ON の LRH1（`local_role_handoff.mjs`）は、自分の観測だけで局所的に役割を切り替える仕組みで、全員が共有する役割割当てではありません。そのためか、球志向の人数は変わっていません。
- **次に実行すべき最小検証**：試合を分岐させない**判断単位の反実仮想**。`choose()` は1選手の知覚DTOだけを入力とする純関数で、DTOは `decision` イベントの `observation` に含まれています。C-1〜C-4 と X-1 の各tickで全選手のDTOを保存しておき、別スクリプトで「自分の観測で球に近い順に2位以内なら球へ、それ以外は球とゴールの間の中央を担当」といった代替の順位付けを当て、同じDTOで球志向の人数、目標の重なり、ゴール側の残り人数がどう変わるかを数えます。自然試合での比較は、その後に行います。
- **関連する既存成果**：I13（近接pairのON/OFF）、I14・I15・I16（SOC11の準備と継続ガード。未採用）、LRH1、別チャットのSOC44/45（役割補完。未統合）。いずれも「人数・距離だけの譲り」は採用しない方針と矛盾しないよう、具体的な仕事（press／中央の保護／縦パスのコース）で照合する必要があります。

### 課題2　スローインが機能しない：自陣方向への無接触スローインが相手CKを生む

- **具体例**：K-4（771 OFF、tick 6860–7010）、K-5（600613 OFF、6940–7090）。
- **確認できた事実**：§4.4 のとおり。受け手の制御 2.3%、相手CKへの転化 83本（OFF）/ 85本（ON）/ 48本（CK枝）。条件によらず同じ傾向です。CKの26%、再開時間の多くがこの連鎖に起因しています。
- **原因仮説**：`decision.mjs` の17〜18行目で、スローの受け手を「4〜28m内で最も近い味方」として選んでおり、方向（自陣ゴール方向か）や相手のマークを考慮していません。受け手は再開中 restart_position のままで、`throw_in_play` の後の判断周期で receive に移ります。スローの速さは `throw_in.mjs` の throwProfile で決まり、受け手の到達時間とは結び付けられていません。この3点の重なりが疑われます。
- **最小検証**：OFF 6試合のスローイン各回について、配置tick（`restart_placement`）以前の最も近いsaveから再現し、キッカーの候補集合、選ばれた受け手の方向、相手との距離、受け手の判断がreceiveに入るまでのtick数を記録します。その後、課題1と同じく判断単位で「後方・被マークの受け手を除外する」などの代替を当て、件数を比べます。
- **関連する既存成果**：`throw_contract.mjs` / `throw_in.mjs`（手と身体の制約）、I14（ONで再開が増えた事実）、I7（再開時間増は戦術悪化と断定しない、という注記）。スローの配球を対象にした既存研究は、同梱資料からは見つかりませんでした。

### 課題3　保持の判断（球から2.1m）が揺れ、パスのたびにチームが守備形へ戻る

- **具体例**：D-2（771 OFF、45:36、tick 54680–54930）、P-1（受け手がcoverのまま奪われる、0:29）。全クリップでの、パス飛行中の色の変化（緑→青）。
- **確認できた事実**：§4.2 の表。自チームのパス飛行中に cover が 57.3%、support↔cover の切替が 18回/人/分。ONでも cover 56.3%、切替 18.0回で同じです。
- **原因仮説**：`decision.mjs` の42行目で `ourPossession = 見えている保持者 ? そのチーム : (2.1m以内に味方あり かつ 敵なし)` としており、球が誰の2.1m以内にもない飛行中やルーズの時は、全員が cover を選びます。味方が蹴った事実（自分で観測できる）が、保持の判断に入っていないと読めます。
- **最小検証**：課題1と同じく、記録したDTOで「直近に観測した味方のキック以降、他の誰も触れていない」を保持の判断に加えた場合、何人が support に変わるかを数えます。**受け手本人の受球意図はちゃつぴ側（R2、パス原則）の領域なので、受け手以外の陣形だけに範囲を限定します。**
- **関連する既存成果**：別チャットのR2（受球後の意図）、SOC23（outlet attention）、early_ball_intent。重複を避けるため、実装前に照合が必要です。

### 課題4　パス → 受球 → 次プレーの連結（ちゃつぴ側へ証拠付きで引渡し）

- **具体例**：P-1（受け手がcoverのまま）、P-2（味方が先取り）、P-3（高速パスの取り損ね）。対照：X-2。
- **確認できた事実**：§4.3。
- **原因仮説**（推測にとどめる）：(a) 受け手が保持の判断を誤り（課題3）、飛行中に受球へ入らない。(b) 出し手の球速が、受け手の制御限界を上回る。(c) 受け手の受球が他の味方と共有されず、別の味方が球を先取りする（課題1）。
- **本監査で行わないこと**：受球予測、パス意図の通知、R2、未採用のパス原則候補の作り直しや採用。
- **引渡し物**：`HANDOVER_pass_reception_cases.json`。OFF 6試合・パス4,417本を母数に、分類A〜D と対照Xについて、tick、出し手、受け手、球速、受け手の判断の割合、最初の接触の相対速度、再現用saveを列挙しています（§7）。

### 課題5　CK：standardは攻撃配置がなく、研究枝は混合候補で停止する

- **具体例**：K-1 / K-1b（771、同条件の最初のCK比較）、K-2（味方の非制御接触から自陣ゴールラインを割る）、K-3（研究枝が停止する直前）。
- **確認できた事実**
  - 同条件の最初のCK（4 seed、どちらの枝も placement 直後まで同一で、+4tickで分岐）：standard は4/4でPA内の攻撃側0人、守備側が先触。CK研究枝は攻撃3〜4人 / 守備10人で、攻撃側の先触2/4、10秒以内のシュート0/4、準備時間は約10秒。
  - 研究枝の停止：771 tick 57055、1847 tick 36328、8081 tick 63655、600613 tick 105210。いずれも `I5_CK_MIXED_GROUP_NOT_CONNECTED`（`integration_i8_ck_research/core/ball.mjs` 58行目）。**4本とも直前のsave（771:54000 / 1847:36000 / 8081:60000 / 600613:102000）から同じtickで停止を再現**しました。いずれも corner_cross の約32tick（1.6秒）後の空中競合で起きています。771の停止直前の候補は次のとおり：A10 corner_header（同時に press がpending）、B07/B08 corner_clear、B00 gk_punch、B05/B09 receive。CKの空中競合と通常の判断が同じtickの同じキック群に入っています。I8 README で「未接続・明示停止」とされている組合せが、**自然試合で4/5の頻度で起きる**ことを確認しました。
- **原因仮説**：standard側は `decision.mjs` 23行目（キッカーの受け手を4〜38m内に限定）と30行目（他の選手は陣形の基準位置を (r.x−52.5)×0.42 だけずらすだけ）で、CK専用の配置がありません。研究枝側は、空中競合と通常キックの裁定が未定義です。
- **最小検証**：(a) 4本の停止saveから停止tickを再現し、候補群を記録したうえで、裁定の契約（どちらを優先し、どう保存するか）を決めます。自然試合の比較は、それまで行いません。(b) CKの効果比較は「同条件の最初のCK」に限ります。2本目以降は機会自体が違います。CKの総数も、standard 54本/試合に対して研究枝は別の試合展開なので比べません。
- **関連する既存成果**：I5 / I7 CK研究枝（未採用）、P0 CK左右の修正（標準に接続済み）、I7追加監査、I8 README の残件、I12（CK研究はSOC OFFでの比較のみ）。

## 8. 再現方法

`audit_pack/` 内で、I17を展開したフォルダを `I17` とします。

```
# 1) フル試合を記録（runs/<名前>/ に pos/dec/tgt バッファ、events.jsonl、decisions.jsonl、6000tickごとのsave、meta.jsonを出力）
node tools/rec.mjs <I17> standard 771 110000 baseline runs/std_off_771 6000
node tools/rec.mjs <I17> standard 771 110000 soc-existing-on runs/std_on_771 6000
node tools/rec.mjs <I17> ck_research 771 110000 baseline runs/ck_off_771 6000
node tools/rec.mjs <I17> standard 4049 110000 baseline runs/std_off_4049_koB 6000 '{"kickoffTeam":"B"}'
# 2) 解析・集計
node tools/analyze.mjs runs/std_off_771
node tools/aggregate.mjs runs agg.json && python3 -I tools/crossrun.py agg.json runs
# 3) saveからの決定的再現の確認（記録した位置と完全一致を確認）
node tools/replay_check.mjs <I17> runs/std_off_771 save_12000.json 4000
# 4) CK研究枝の停止の再現
node tools/crash_repro.mjs <I17> ck_research runs/ck_off_771/save_54000.json
# 5) 2Dビューア（clips_spec.json を編集して再生成）
node tools/clip.mjs tools/clips_spec.json clips.json && python3 -I tools/build_viewer.py tools/viewer_template.html clips.json I17_audit_viewer.html
```

- 1本あたり約11分（Node 22、4並列時）。記録はエンジンを `research_guard.mjs` の `register` / `create` / `restore` 経由でのみ使い、ソースは変更していません。
- 再現の確認結果：std_off_771 の save_12000 から4,000tick、ck_off_771 の save_6000 から600tick、std_on_771 の save_54000 から1,200tick を再生し、選手22人と球の位置が記録と**完全一致**（誤差0）。
- 同梱saveは、クリップと停止再現に必要なものだけです（`repro_saves/`）。全runの全saveは容量のため同梱していません（約660MB）。同じseed・同じ設定で `rec.mjs` を再実行すれば再生成できます。
- 2Dビューア `I17_audit_viewer.html`：18クリップ（問題例と対照）。同期した2画面で比較（K-1 / K-1b）。判断kindごとの色分け、判断目標の点線、球の軌跡、イベント列を表示。ブラウザで開くだけで使えます（Chromium/Playwrightで描画を確認）。
